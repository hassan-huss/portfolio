SQL injection and XSS

Injection

  • SQL injection happens when an app pastes my input into the query text. The real fix is a parameterized query: the query and the data travel separately, so data can never turn into code.

    Preventing SQL injection

  • When the page shows nothing, the database can still answer yes-or-no questions. In PortSwigger labs I used Burp Intruder to rebuild a password from a "Welcome back" message, and confirmed another injection through a DNS lookup to Burp Collaborator.

    Blind SQLi lab Out-of-band lab

  • Stored safely is not the same as safe. In second-order injection, a username is saved harmlessly at signup, then a later query trusts it and runs it.

    Second-order SQL injection

  • For XSS, where my input lands (between tags, inside an attribute, inside a script) decides how it breaks out. The defence is encoding output for that exact spot, not blocking a list of bad words.

    Cross-site scripting
IDOR

Access control

  • IDOR is an authorisation bug, not a login bug. The app knows who I am but never checks whether the record I asked for is mine.

    Authentication vs authorisation

  • Encoding or hashing an ID only makes it harder to guess. Random IDs still leak, so I test with two accounts: take an ID from one and request it as the other.

    Forms an ID takes

  • IDs don't only live in the address bar. They travel in background API calls, JavaScript files, cookies and request bodies, so I check every request in the browser's Network tab.

    Where IDOR hides

  • The same missing check on a write, like changing an email, is an account takeover, not just a leak. The fix is one ownership check on the server for every request.

    Mitigation
SSRF

Server-side requests

  • Features that fetch a URL for you, like link previews and avatar imports, run from inside the network. Steer them and you reach internal pages the internet can't.

    Why SSRF works

  • Blind SSRF returns no content, so it is confirmed by making the server call back to a listener, or by differences in timing and errors.

    Regular vs blind

  • The biggest target is the cloud metadata service: an internal address that hands temporary credentials to anything asking from inside the server.

    Impact

  • In the lab, a filter checked the path before the server tidied it up, so a harmless-looking path became a blocked one. Check the final destination, not the raw text.

    The avatar lab
Nmap and web server rooms

Recon and web servers

  • My Nmap order: find which hosts are alive, scan ports on those, then identify the service and version behind each open port. Each step decides the next scan.

    Four Nmap rooms

  • Every web server introduces itself: in the Server or X-Powered-By header, or in its default 404 page when headers are hidden. Express sends no Server header by default, so a missing one is a clue too.

    Identifying web servers

  • A version in a header is a lookup key. An IIS version tells me which Windows Server sits underneath and which CVEs apply, and an Apache 2.4.49 banner points straight to a known path-traversal bug.

    IIS fingerprinting Apache on LAMP

  • Most findings are defaults nobody reviewed. Across the four lab servers (Apache, Nginx, Node and Python) that meant versions in headers, directory listings, status pages and leftover files. None sent security headers.

    Patterns on every server

An autonomous firefighting robot.

My Intro to Engineering final project at LIU: a four-wheel-drive Arduino car that finds a flame with analog sensors and puts it out with a water sprayer, with no one driving it. I simulated the circuit in Tinkercad first, then built it and wrote the firmware.

  1. 1
    Arduino UNO. Runs the firmware: reads the sensors, decides, and drives the motors and sprayer.
  2. 2
    L298N motor driver. Takes the Arduino's signals and powers the four DC motors.
  3. 3
    18650 battery. Onboard power, so the car runs untethered.
  4. 4
    Flame sensor wiring. Carries the analog flame readings back to the Arduino.
  5. 5
    4WD chassis. Four DC motors, one for each wheel.

Parts

  • Arduino UNO, the controller
  • L298N dual H-bridge motor driver
  • 4 DC motors on a 4WD chassis
  • Analog flame sensors
  • Water sprayer to put the flame out
  • 18650 batteries for power

What I built

  • The motor control for a 4WD chassis through the L298N driver
  • Flame detection that uses the analog sensor readings to work out which way the fire is
  • A water sprayer that switches on by itself when a flame is detected
  • The full circuit in Tinkercad, simulated before building
  • The Arduino firmware for sensing, decisions, and motor and sprayer output

What I learned

  • Turning raw sensor input into real-time decisions with no one at the controls
  • Motor driver wiring, PWM speed control, and how an H-bridge behaves
  • Simulating first catches design mistakes before they're built into the hardware
  • Debugging where the code and the electronics meet
  • Real sensors are noisier than any simulation lets on

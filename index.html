University project · LIU · Introduction to Engineering

Autonomous firefighting robot

A four-wheel-drive Arduino car that locates a flame with analog sensors and puts it out with a water sprayer, with no human input.

  • Arduino UNO
  • C++
  • L298N
  • Tinkercad
My part
Circuit design and simulation, hardware build, firmware
Type
Final project, Introduction to Engineering
Process
Simulated in Tinkercad first, then built and programmed
  1. 1
    Arduino UNO. Runs the firmware: reads the sensors, decides, and drives the motors and sprayer.
  2. 2
    L298N motor driver. Dual H-bridge that takes the Arduino's signals and powers the four DC motors.
  3. 3
    18650 battery. Onboard power, so the car runs untethered.
  4. 4
    Flame sensor wiring. Carries the analog flame readings back to the Arduino.
  5. 5
    4WD chassis. Four DC motors, one for each wheel.

What I built

  • Motor control for a 4WD chassis through the L298N, with PWM speed control
  • Flame detection that uses the analog readings to work out which way the fire is
  • Automatic sprayer that switches on when a flame is detected
  • Arduino firmware (C++) for sensing, decisions, and motor and sprayer output

Engineering decisions

  • Simulate first. The full circuit ran in Tinkercad before wiring, catching design mistakes before they reached hardware
  • Analog flame sensors, so the readings show which way the fire is, not only whether there is one
  • Onboard battery power so the robot runs with no tether

Challenges and lessons

  • Real sensors are noisier than any simulation lets on
  • Debugging where the code and the electronics meet
  • Turning raw sensor input into real-time decisions with no one at the controls

Recon first: fingerprint the target and map what's there before touching anything. Then I write the lab up, because explaining it shows me what I still don't understand.

PortSwigger · SQL injection and XSS

Injection

  • When the page shows nothing, the database can still answer yes-or-no questions. I used Burp Intruder to rebuild a password from a "Welcome back" message, and confirmed another injection through a DNS lookup to Burp Collaborator.

    Blind SQLi lab Out-of-band lab

  • The real fix is a parameterized query: the query and the data travel separately, so data can never turn into code. Stored safely is not the same as safe, which is what second-order injection shows.

    Preventing SQL injection Second-order SQLi
TryHackMe · IDOR

Access control

  • IDOR is an authorization bug, not a login bug. Encoding or hashing an ID only makes it harder to guess, so I test with two accounts and check every request in the Network tab, including background API calls.

    Where IDOR hides

  • The same missing check on a write, like changing an email, is an account takeover, not just a leak. The fix is one ownership check on the server for every request.

    Mitigation
TryHackMe · SSRF

Server-side requests

  • Features that fetch a URL for you run from inside the network. The biggest target is the cloud metadata service, which hands temporary credentials to anything asking from inside the server.

    Impact

  • In the lab, a filter checked the path before the server tidied it up, so a harmless-looking path became a blocked one. Check the final destination, not the raw text.

    The avatar lab
TryHackMe · Nmap and web servers

Recon and fingerprinting

  • My Nmap order: find live hosts, scan their ports, then identify the service and version on each open port. Each step decides the next scan.

    Four Nmap rooms

  • Most findings are defaults nobody reviewed. Across four lab servers (Apache, Nginx, Node and Python) that meant versions in headers, directory listings and leftover files. None sent security headers.
